# STEP-03 — Internal Branches and Valid / Invalid Scenarios\n\nSTEP-02 defines the programmatic contracts of the Intent Trajectory. STEP-03 decomposes every contract into internal decision branches and defines valid and invalid scenarios for each branch.\n\nThe rule for every stage is:\n\n    Input -> Preconditions -> Internal branches -> Valid scenarios -> Invalid scenarios -> Output\n\nAn invalid scenario must never be silently converted into a valid one.\n\n## 1. Intent — origin branches\n\nBranches:\n- actor present or explicitly unresolved\n- expression present\n- desired outcome explicit, absent, or unresolved\n- entities identifiable or unresolved\n- constraints present or absent\n- temporal conditions present or absent\n- authorization context present or absent\n- provenance present\n- pre-existing contradictions represented\n\nValid scenarios:\n- stable identity and preserved original expression\n- optional information absent without corrupting Intent\n- ambiguity or missing outcome explicitly represented\n- provenance retained\n\nInvalid scenarios:\n- original Intent rewritten\n- missing outcome invented\n- actor guessed and stored as fact\n- provenance discarded\n- separate Intents merged without explicit equivalence\n- later Action mutates original Intent\n\nInvariant: OriginalIntent is immutable.\n\n## 2. Understanding — interpretation branches\n\nBranches:\n- expression interpretable\n- actor identifiable\n- desired outcome identifiable\n- entities identifiable\n- requirements separable\n- ambiguity present\n- contradiction present\n- missing information present\n- temporal meaning present\n- uncertainty present\n\nValid scenarios:\n- clear Intent becomes UnderstoodIntent\n- ambiguity becomes explicit ambiguity\n- contradiction remains contradiction\n- missing information remains explicit\n- inferred requirements are marked inferred\n- uncertainty is preserved\n\nInvalid scenarios:\n- ambiguity silently resolved\n- inference stored as explicit requirement\n- contradiction removed\n- missing information invented\n- Understanding executes an Action\n- Understanding creates Goal or Destination prematurely\n\nPossible outcomes: Understood, UnderstoodWithUncertainty, NeedsClarification, Contradictory, Unresolvable.\n\n## 3. Normalization — meaning-preservation branches\n\nBranches:\n- equivalent canonical representation available\n- explicit requirements preserved\n- inferred requirements remain inferred\n- ambiguities preserved\n- contradictions preserved\n- temporal semantics preserved\n\nValid scenarios:\n- equivalent expressions normalize to equivalent meaning\n- representation changes without semantic change\n- uncertainty survives normalization\n\nInvalid scenarios:\n- desired outcome changed\n- constraint removed\n- inference promoted to fact\n- ambiguity resolved without authority\n- contradiction removed\n- new requirement introduced\n\nRequired invariant: meaning(before) == meaning(after).\n\n## 4. Contextualization — relevance branches\n\nBranches:\n- context available or explicitly absent\n- candidate context relevant or irrelevant\n- context authoritative or non-authoritative\n- context temporally valid or stale\n- context conflicts with existing facts\n- context changes interpretation, constraints, or available paths\n\nValid scenarios:\n- relevant context attached\n- historical and current context distinguished\n- stale context rejected or marked stale\n- conflicts represented explicitly\n- context affects planning without rewriting Intent\n\nInvalid scenarios:\n- all available context blindly attached\n- irrelevant context becomes constraint\n- stale context treated as current fact\n- context overwrites Intent\n- untrusted observation becomes authoritative without basis\n- context silently changes Goal\n\nPossible outcomes: Contextualized, ContextuallyIncomplete, ContextConflict, ContextStale, ContextInsufficient.\n\n## 5. Goal — outcome branches\n\nBranches:\n- desired outcome exists\n- outcome is semantically expressible\n- outcome is traceable to Intent\n- outcome is distinguishable from Action\n- success meaning is definable\n- required semantic change is identifiable\n\nValid scenarios:\n- Goal expresses desired semantic outcome\n- Goal has success meaning\n- Goal is traceable to Intent\n- Goal remains implementation-independent\n\nInvalid scenarios:\n- Goal is a tool call\n- Goal is a function or endpoint\n- Goal is an implementation step\n- Goal introduces a new objective\n- Goal removes an original requirement\n- Goal cannot be traced to Intent\n\nInvariant: Goal != Action, Goal != Tool, Goal != Implementation.\n\n## 6. Constraints — boundary branches\n\nBranches:\n- constraints discoverable or explicitly absent\n- predicate exists\n- source exists\n- scope exists\n- applicability known\n- severity known\n- violation meaning defined\n- conflicting constraints detected\n\nValid scenarios:\n- zero or many constraints explicitly represented\n- conditional constraints represented as conditional\n- constraints remain active across transitions\n\nInvalid scenarios:\n- constraint exists only in free text\n- no evaluable predicate\n- executor removes constraint because execution is difficult\n- planner ignores active constraint\n- conflicting constraints silently merged\n- violation hidden from evaluation\n\nPossible outcomes: ConstraintsValid, NoConstraints, ConstraintConflict, ConstraintUndetermined, ConstraintViolation.\n\n## 7. Destination — completion branches\n\nBranches:\n- required outcome\n- required final state\n- required evidence\n- completion conditions\n- failure conditions\n- validation rules\n- traceability to Goal\n\nValid scenarios:\n- semantic completion state is explicit\n- required evidence is explicit\n- completion and failure are distinguishable\n- Destination is independently evaluable\n\nInvalid scenarios:\n- Destination is an Action\n- Destination is merely an API success\n- Destination is merely workflow completion\n- Destination is invented after execution\n- Destination changes because a plan failed\n- required evidence omitted\n- completion predicates cannot be evaluated\n\nInvariant: Destination defines WHAT must be true, not HOW it becomes true.\n\n## 8. Semantic State — state branches\n\nBranches:\n- predecessor known\n- facts have provenance\n- conditions evaluable\n- unresolved conditions explicit\n- contradictions explicit\n- temporal position valid\n\nValid scenarios:\n- initial state contains known or explicitly unknown conditions\n- derived state references predecessor\n- new facts have provenance\n- contradictions retained\n- Unknown remains Unknown\n\nInvalid scenarios:\n- state appears without origin\n- historical state overwritten\n- Unknown becomes True without evidence\n- contradictory facts silently collapsed\n- unproven facts become authoritative\n- temporal order is undefined\n\n## 9. Trajectory Planning — path branches\n\nBranches:\n- valid transition exists\n- every transition has objective\n- preconditions defined\n- expected changes defined\n- constraints respected\n- validation points defined\n- alternatives available where required\n\nValid scenarios:\n- plan contains semantic transitions\n- each transition has an objective\n- constraints are respected\n- alternatives and failure points are represented\n\nInvalid scenarios:\n- plan is only a list of tool calls\n- transition has no semantic objective\n- plan violates a known constraint\n- planner changes Goal\n- planner changes Destination to make itself succeed\n- impossible transition accepted as executable\n\nPossible outcomes: PlanAvailable, PlanWithAlternatives, Blocked, Undetermined.\n\n## 10. Transition — local execution branches\n\nBranches:\n- preconditions satisfied\n- required constraints satisfied\n- required Action available\n- Action executes\n- observation produced\n- expected change observed\n- postconditions satisfied\n\nValid scenarios:\n- Action implements a declared Transition\n- successful execution produces Evidence\n- partial success produces partial state\n- failure becomes TransitionResult\n- Unknown postcondition remains Unknown\n\nInvalid scenarios:\n- preconditions bypassed\n- Action executed without Transition objective\n- Action success treated as Destination success\n- failure hidden\n- partial state discarded\n- postcondition assumed without evidence\n\nLocal outcomes: TransitionSucceeded, TransitionPartiallySucceeded, TransitionFailed, TransitionBlocked, TransitionUndetermined.\n\n## 11. Action — implementation branches\n\nBranches:\n- Action required\n- Action authorized\n- Action available\n- Action executed\n- result observable\n- result mapped to semantic Evidence\n\nValid scenarios:\n- one or many Actions implement one Transition\n- Action failure remains potentially recoverable\n- Action success does not automatically prove semantic postcondition\n\nInvalid scenarios:\n- Action creates or changes Goal\n- Action creates or changes Destination\n- Action removes Constraint\n- Action declares global success\n- raw Action result becomes fact without Evidence mapping\n\n## 12. Evidence — truth branches\n\nBranches:\n- source known\n- temporal position known\n- observed fact explicit\n- supports condition\n- contradicts condition\n- quality/confidence known when relevant\n\nValid scenarios:\n- evidence supports a condition\n- evidence contradicts a condition\n- evidence is insufficient\n- multiple observations agree\n- multiple observations conflict and remain represented\n\nInvalid scenarios:\n- evidence has no provenance\n- evidence silently overwritten\n- expected result fabricated as observation\n- absence of evidence becomes success\n- contradictory evidence discarded\n\nPossible outcomes: Supports, Contradicts, Insufficient, Conflicting, Unusable.\n\n## 13. Transition Evaluation — control branches\n\nBranches in order of semantic severity:\n- constraint violation -> Invalidated\n- blocking condition -> Blocked\n- unresolved critical condition -> Undetermined\n- all Destination predicates may be satisfied -> Validate\n- current plan remains valid -> Continue\n- current plan is no longer valid -> Replan\n\nValid scenarios:\n- local progress leads to Continue\n- impossible path leads to Replan\n- impossible requirement leads to Blocked\n- contradiction prevents certainty and leads to Undetermined\n- possible completion leads to Validate\n\nInvalid scenarios:\n- constraint violation ignored\n- Unknown converted to success\n- evaluator declares Destination reached directly\n- replanning changes Goal\n- contradictory evidence discarded\n\nNormative precedence:\n\n    Invalidated > Blocked > Undetermined > Validate > Replan > Continue\n\n## 14. Replanning — recovery branches\n\nBranches:\n- Goal still valid\n- Constraints still satisfiable\n- Destination still valid\n- current state sufficient\n- alternative transition exists\n\nValid scenarios:\n- failed Action has another implementation\n- failed Transition has another semantic path\n- new evidence changes route\n- original plan becomes impossible while Goal remains valid\n\nInvalid scenarios:\n- Destination silently changed\n- constraints removed\n- Intent changed\n- failed evidence forgotten\n- infinite replanning without state or evidence change\n\nInvariant: NewPlan.originState == CurrentState and NewPlan.destination == ExistingDestination.\n\n## 15. Destination Validation — global truth branches\n\nBranches:\n- required outcome satisfied\n- final state satisfied\n- required evidence sufficient\n- constraints satisfied\n- completion conditions satisfied\n- failure conditions triggered\n- unresolved contradictions present\n\nValid outcomes:\n- all required predicates true + sufficient evidence + constraints satisfied -> Reached\n- completion predicates false while completion remains possible -> NotReached\n- required condition cannot currently be established -> Undetermined\n- required condition cannot be satisfied under active boundaries -> Blocked\n- terminal invariant violated or Destination invalidated -> Invalidated\n\nInvalid scenarios:\n- Action success causes Reached\n- Transition success causes Reached\n- missing evidence ignored\n- constraint violation ignored\n- Unknown treated as True\n- failure condition ignored\n- Destination changed to match current state\n- validation relies only on final Action result\n\n## 16. Terminal Outcome — closure branches\n\nBranches: Reached, NotReached, Blocked, Invalidated, Undetermined.\n\nValid terminal result contains:\n- Destination identity\n- final SemanticState\n- supporting and contradicting Evidence\n- satisfied and unsatisfied conditions\n- constraint status\n- provenance\n- termination reason\n\nInvalid scenarios:\n- generic Success/Failure hides semantic distinction\n- terminal result has no evidence\n- terminal result cannot be traced to Destination\n- terminal result contradicts validation\n- terminal trajectory silently receives new Actions\n\n## 17. Cross-stage branches\n\n### Clarification\n\nValid: missing information is explicitly requested and additional information is linked to the original Intent.\nInvalid: missing information is invented or execution proceeds on an arbitrary assumption.\n\n### Contradiction\n\nValid: conflicting claims remain traceable; explicit new evidence may resolve them; unresolved contradiction remains Undetermined.\nInvalid: one claim is silently deleted, or latest observation automatically wins.\n\n### Partial progress\n\nValid: partial state and Evidence are retained and planning continues or replans from actual state.\nInvalid: partial success is promoted to complete success or discarded.\n\n### No-op transition\n\nValid: no semantic state change is expected because the Transition is observational and produces useful Evidence.\nInvalid: a transition claims progress while producing neither semantic change nor new Evidence.\n\n### Repeated transition\n\nValid: repetition is explicitly allowed and has a bounded retry or a new reason/state/Evidence.\nInvalid: infinite repetition without state/evidence change or retry boundary.\n\n### Terminal protection\n\nValid: a new Intent or explicit recovery contract creates a new trajectory.\nInvalid: terminal history is overwritten or Actions are silently appended to a terminal trajectory.\n\n## 18. Global valid trajectory\n\n    Intent -> UnderstoodIntent -> NormalizedIntent -> ContextualizedIntent\n    -> Goal -> Constraints -> DestinationContract -> CandidateTrajectory\n    -> Transition -> Action(s) -> Evidence -> SemanticState\n    -> TransitionEvaluation -> Continue/Replan/Validate\n    -> DestinationValidation -> Reached\n\nEvery transition between these concepts has a defined responsibility, validation boundary, and traceability.\n\n## 19. Global invalid trajectories\n\n    Intent -> Action -> Success\n\n    Intent -> Tool -> ToolResult -> NewGoal\n\n    Intent -> Actions -> inspect_result -> invent_Destination\n\n    PlanFailure -> change_Destination -> continue\n\n    NewEvidence -> delete_ContradictoryEvidence\n\n    Unknown -> True -> Reached\n\n    ConstraintViolation -> ignore -> Continue\n\n    ActionSuccess -> DestinationSuccess\n\n    Failure -> Retry -> Failure -> Retry -> ...\n\nAll are forbidden because they collapse semantic responsibility or destroy evidence.\n\n## 20. Branch classification contract\n\nEvery implementation branch must be classified as one of:\n\n    VALID_PROGRESS\n    VALID_NO_PROGRESS\n    VALID_RECOVERY\n    VALID_TERMINAL\n    INVALID_INPUT\n    INVALID_STATE\n    INVALID_TRANSITION\n    INVALID_EVIDENCE\n    INVALID_CONSTRAINT\n    INVALID_DESTINATION\n    INVALID_TERMINATION\n\nA branch must not exist only as an undocumented exception or hidden control path.\n\n## 21. STEP-03 completion criterion\n\nSTEP-03 is complete when every semantic component from STEP-02 has explicit internal branches, valid scenarios, invalid scenarios, branch outcomes, preservation rules, recovery rules where applicable, and terminal rules where applicable.\n\nThe test derivation contract is:\n\n    Scenario -> Input State -> Branch -> Expected Semantic Result\n             -> Expected Evidence -> Expected Next State -> Expected Outcome\n\nThe purpose of STEP-03 is to define the complete semantic branching surface of the Intent Trajectory so implementation and testing do not need to invent undocumented semantics.
